# 摄像头实时检测

内置／USB摄像头已接入现有检测、连续确认、分级报警、SQLite日志、截图和前后片段流程。入口仍在 `Demo Videos`，本地视频功能继续保留。

## 操作步骤

1. 启动项目，打开 [检测页](http://127.0.0.1:8501/Demo_Videos)，在“视频来源”选择“摄像头”。
2. 默认编号0使用本机第一个摄像头。外接设备可尝试编号1等；默认“自动”在Windows使用DirectShow，必要时选择Media Foundation。
3. 选择模型、CPU／GPU，并按需要调整报警与录制设置。点击“开始检测”后才打开设备，显示最新画面、检测框、当前等级、本段已检测帧数、本段时间、处理速度和跳过的过时采集帧。
4. 默认沿用连续3个采样帧、0.5秒关注／2秒预警／5秒报警；烟雾可独立触发。首次确认时保存截图，并收集确认前5秒、后10秒的片段。
5. “暂停检测”关闭设备、结束当前观测段并保存已有片段，页面保留最后画面和等级。“继续检测”重新打开设备、建立新观测段并重新累计证据。暂停期间未观察到的画面不会用于持续确认或恢复。
6. “停止检测”释放设备。进入 `Alarm History`，按来源选择“摄像头0”等记录，可查看等级变化、截图和片段，或导出CSV。生成中的片段完成后自动刷新。
7. 摄像头不可用、被占用、超时或断流时会显示原因，关闭设备并保留最后报警判定。修复后点击“开始检测”重新观测。

这里使用的是运行Python服务的那台电脑连接的摄像头，不是远程浏览器／手机的摄像头；当前不接入RTSP和网络摄像头地址。摄像头权限由Windows控制，程序不会修改系统权限。无法打开时检查系统摄像头访问设置、物理遮挡／开关，以及占用设备的其他应用。

## 时间、暂停与断流

视频文件按原始时间戳逐帧处理；实时摄像头按主机成功取帧时的单调时钟计时，每个观测段从首次处理的采集帧开始计时。持续几秒的规则不依赖页面刷新次数、设备报告帧率或电脑日期调整。它是主机取帧时间，不是传感器硬件时间戳。

实时流只保留最新交付画面，慢于采集时跳过旧帧，不累积待推理队列。“连续帧”表示连续被检测的采样帧，不能理解为每一帧摄像头原始图像均参与推理。设备报告帧率、实际处理速度和跳过帧数分别显示。

暂停会终止当前事件的观察，结束原因为“暂停观测”，最后等级保持原值。继续后有新的运行编号、观测段编号和相对时间；旧记录继续保留。同一未中断的观测段内，持续事件仍沿用同一个事件编号，不会每帧重复建事件。

断流或过长的检测间隔不表示火烟消失。默认相邻检测帧超过报警配置的1秒间隔上限时会结束本段，记录“摄像头观测中断”，保留最后等级，重新开始后再确认。若设备或CPU过慢，需结合实际处理速度调整配置，不能仅凭恢复等待时间把未观察区间当作正常画面。

离开页面、关闭浏览器等导致不再轮询时，摄像头默认15秒后自动关闭；即使页面不再处理新帧，后台也会结束日志并收尾已有片段。取帧停滞默认3秒后关闭。正常停止、暂停或中断都不会自动新增“火情已恢复”记录。

## 配置与日志

[configs/camera.json](../configs/camera.json) 中的默认值：

|参数|默认值|含义|
|---|---:|---|
|index|0|摄像头编号，支持0～9。|
|backend|AUTO|Windows自动选择DirectShow；也可明确选择DSHOW或MSMF。|
|width／height|640／480|请求并限制交付画面的最大尺寸，实际尺寸以设备结果为准。|
|fps|30|请求采集帧率，不保证设备实际达到该值。|
|open_timeout_seconds|8|打开设备与首帧的最大等待。|
|read_timeout_seconds|3|没有收到新画面的超时。|
|idle_timeout_seconds|15|页面不再取画面时自动关闭的等待。|

摄像头在独立进程中采集，主进程保存一份最新帧；超时可终止采集进程，避免驱动读取阻塞拖住页面。一个服务进程内同一编号只能被一个会话持有，停止后可重新打开。传输采用JPEG编码，随后使用与文件输入相同的检测、报警和媒体处理函数。

日志在 `runs.metadata_json` 中增加 `input_type=camera`、主机单调时钟标记、摄像头参数、采集后端、会话编号和观测段编号。媒体记录也注明输入类型；事件编号与媒体保存方式沿用现有结构，无需删除旧数据库。CSV新增“输入类型”列，并保留原来的“视频”等列名兼容旧导出格式；摄像头行里的相对秒数指当前观测段时间，实际日期仍见UTC记录时间。

截图、H.264静音片段和数据库默认仍在 `artifacts/alarms/`，不随commit／push上传。片段不足时会说明实际范围。录制上限、编码器和存储说明见 [recording.md](recording.md)，报警规则见 [alarm.md](alarm.md)。没有新增pip依赖。

2026-10-20在本机HP True Vision FHD Camera上验证：DirectShow、交付640×480、设备报告约30帧／秒，使用上游 `fire_n.pt` 和CUDA。真实设备完成25帧检测，暂停释放后重新打开再检测8帧；终止实际采集进程后，后台识别中断并释放设备，再次成功打开、检测和停止。实拍验证没有保存个人图像。

|检查|结果|
|---|---|
|已有规则／媒体检查|36项通过。|
|摄像头新增检查|16项通过，包括最新帧、重复轮询、时钟异常、漏采帧、暂停／恢复、断流、超时、自动关闭、设备占用与释放。|
|受控摄像头链路|黑帧后切换公开样例，190个受控时间戳采样帧，真实YOLO推理；形成1个最高报警级事件。|

真实设备验证用于证明摄像头读取和检测流程可用；火烟升级与媒体验证使用公开样例和受控时序，未进行实火／实烟试验。断流与阻塞在自动检查中使用可控采集进程模拟，另验证了实际设备采集进程中断；没有把它写成人工拔插硬件试验，也不据此报告模型准确率。

真实Edge浏览器另验证了摄像头检测、暂停帧数稳定、继续新段、停止后按钮恢复，以及公开样例摄像头事件的截图解码、15秒视频播放与进度拖动。实际重启服务后，历史和媒体仍可查看、回放，未出现页面或媒体请求错误。

## 复验

在项目目录运行，默认会使用本机摄像头：

```powershell
.\.venv\Scripts\python.exe .\scripts\verify_camera.py
```

脚本执行52项检查、实际设备启停、受控报警媒体、四段完整文件回归和页面检查。实拍环节只记录帧数、尺寸和状态，不保存个人画面；生成的媒体来自公开样例。

没有摄像头的电脑可显式加 `--skip-hardware`，报告会标为 `passed_without_hardware`，不能视为设备验收通过。单独运行新增检查：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_camera.py -v
```

[verify_camera_browser.mjs](../scripts/verify_camera_browser.mjs) 使用Playwright／Edge验证实际摄像头页面，并关闭实拍录制；再播放公开样例生成的摄像头事件。运行前用 `verify_camera.py --output-dir <测试目录>` 准备数据，让页面服务的 `FIRE_ALARM_LOG_PATH` 指向该目录的 `camera.sqlite3`。重启同一数据库后可用 `--history-only` 复查历史。

实现：[camera_capture.py](../camera_capture.py) 隔离原生设备读取，[camera_source.py](../camera_source.py) 管理最新帧与超时，[camera_session.py](../camera_session.py) 连接既有报警和媒体流程。时钟与采集接口参考 [Python 3.11单调时钟说明](https://docs.python.org/3.11/library/time.html#time.monotonic)、[OpenCV VideoCapture](https://docs.opencv.org/4.x/d8/dfe/classcv_1_1VideoCapture.html)。
