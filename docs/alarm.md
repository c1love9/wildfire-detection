# 连续确认、分级报警与报警日志

视频页在每帧检测后增加时序判定。短暂的单帧检出不直接创建报警事件；同一类别、同一区域连续出现后才确认，再依据源视频中的持续时间升级。烟雾可以独立触发各级提示。

现已加入报警截图、确认前后片段保存和日志页回放，详情见 [recording.md](recording.md)。

## 使用方法

1. 启动项目，打开 [视频检测页](http://127.0.0.1:8501/Demo_Videos)。先使用 `fire1.mov`、`fire_n` 和默认参数。
2. 展开“报警规则”，查看或调整连续帧数、两类报警置信度、各级持续时间和恢复等待。关注、预警、报警时间必须依次增大；无效规则会显示提示并禁用开始按钮。
3. 点击“开始检测”。画面上方显示当前等级、参与判定的类别、当前连续命中帧数和持续时间，以及本次确认的事件数量。关注用蓝色提示、预警用黄色、报警用红色。
4. “本次报警变化”显示最近50条变化。连续事件沿用同一编号，仅记录确认、升降级、恢复或观察结束，不会每帧新建事件。
5. 暂停时画面、视频计时和报警判定保持不变；继续后从下一帧处理。停止或视频结束会保留最后判定，并记录真实结束原因。
6. 从侧边栏进入 `Alarm History`，按视频来源、事件最高等级筛选，查看等级变化和视频时间，或点击“导出当前筛选 CSV”。页面最多展示并导出最近500条匹配事件，点击“刷新记录”重新查询。

本阶段采用界面提示，没有增加声音、短信或外部通知。历史页展示的是确认事件；只有候选框、没有达到确认条件时，不会出现事件行。

## 默认规则

默认值保存在 [configs/alarm.json](../configs/alarm.json)。网页调整仅用于本次检测；修改该文件可改变后续默认值，每次运行会把实际规则快照保存进日志。

|参数|默认值|作用|
|---|---:|---|
|连续确认帧数|3|至少连续3帧命中，还须达到对应持续时间。|
|火焰／烟雾报警置信度|各0.50|报警仅使用达到对应类别阈值的检测框。|
|关注持续时间|0.5秒|达到后首次创建事件并进入关注。|
|预警持续时间|2秒|持续证据足够时进入预警。|
|报警持续时间|5秒|持续证据足够时进入报警。|
|恢复等待|2秒|某等级不再被有效证据支持后，等待2秒才降级或恢复。|
|区域匹配IoU|0.10|相邻检测框需为同一类别且有足够重叠，一对一关联。|
|相邻帧最大时间间隔|1秒|间隔过大时重新累计连续证据，避免时间跳变直接触发高级别。|

这是课程原型的可配置初值，后续应在独立验证视频上选定。正常为0级，关注、预警、报警分别为1、2、3级。各区域独立累计，页面显示所有区域中的最高等级；不同类别或不同位置轮流出现不能拼成一个连续序列。这里的区域关联是简单框匹配，没有把检测框面积当成火灾掩码面积。

帧数与时间条件同时生效。例如30帧／秒时，从首帧时间0开始，默认关注最早在第16帧、预警在第61帧、报警在第151帧满足；不会因为处理或页面刷新变慢而提前报警。低于1帧／秒的素材可能需要提高最大帧间隔配置。

报警置信度与检测置信度分别设置。检测阶段已经过滤掉的框不会进入报警，所以实际有效门槛至少为这两个阈值中的较高值。界面显示的检测框数量仍包含所有满足检测阈值的框，不等于已确认报警数量。

一次漏检会中断连续证据累计，后续重新确认；已经达到的等级在恢复等待内保持，缺少证据时不会继续升级。某区域仍有低等级持续证据时，可以从报警降到关注／预警，事件编号保持不变。所有有效等级都过期后才记录“已恢复”；恢复后再次确认则创建新事件。

暂停不输入新帧，持续时间与恢复等待都不前进。手动停止、视频结束、检测异常只是观察结束，日志保留最后等级，不能据此认定火烟消失。程序被强制关闭时，尚未结束的事件保持“未结束”，重新打开历史页不会把它自动改成已恢复。

## 日志保存与字段

默认数据库为 `artifacts/alarms/alarms.sqlite3`。它保存到本机磁盘，重启后可继续查询；该目录已被Git忽略，不随commit或push上传。运行时SQLite还可能生成同目录的WAL等辅助文件，不要在程序使用数据库时单独删除这些文件。

|表|内容|
|---|---|
|runs|每次检测的独立编号、视频名、记录起止时间、结束原因、报警参数与模型／设备配置快照。|
|events|事件编号、运行编号、确认帧与视频时间、结束帧与时间、类别、最高置信度、最高／最后等级和结束原因。|
|transitions|同一事件的确认、升级、降级、恢复、停止、视频结束或异常，以及对应帧号和视频时间。|

事件的“开始视频时间”指首次达到确认条件的时间，不是人工标注的火灾起点。记录时间使用UTC并在页面列名中明确标注；视频时间是源素材中的秒数，两者分别记录。事件统计在内存更新，在等级变化或结束时写入数据库；异常强制退出可能只保留最近一次已写入的数据。

日志创建失败会阻止开始，并给出提示。运行中写入失败会保留界面检测和报警，但明确提示部分历史可能未保存。监控页只保留最近50条变化，完整已保存记录从历史页查询。

可用环境变量 `FIRE_ALARM_LOG_PATH` 指定独立数据库。验证脚本使用单独数据库，避免把模拟测试事件混入实际使用记录。CSV为带BOM的UTF-8文件，可用Excel打开。

真实Edge浏览器验证了默认规则依次进入三级提示、暂停与继续、停止保留等级、新视频重置证据、短暂检出不确认、历史等级筛选和CSV下载。随后实际重启页面服务，确认同一事件与导出内容仍然保留；未出现页面异常或检测图片请求错误。

样例没有独立的事件真值，部分素材原本还带有旧检测框。这些数字验证流程与过滤行为，不能据此声称真实误报率、漏报率或准确率改善。正式对比应在人工标注的完整正常／火烟视频上，分别报告单帧策略与时序策略的误报事件、漏报事件和首次报警延迟。

## 复验与实现

在项目目录运行：

```powershell
.\.venv\Scripts\python.exe .\scripts\verify_alarm.py
```

脚本执行23项检查、四段完整视频、暂停／停止／异常集成与页面验证，成功后更新JSON报告。仅运行快速规则检查可用：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_alarm.py -v
```

[verify_alarm_browser.mjs](../scripts/verify_alarm_browser.mjs) 是可选的真实浏览器检查，需要已安装Playwright及Edge；不属于应用运行依赖。可通过 `PLAYWRIGHT_MODULE` 指定已有Playwright模块地址，`BROWSER_EXECUTABLE` 指定浏览器。检查时先让页面服务使用一份新的独立日志库，再运行该脚本，避免已有事件影响“一条事件”的断言。服务重启后可使用 `--history-only` 再查同一数据库。

主要实现：[alarm.py](../alarm.py) 负责纯时序判定，[alarm_log.py](../alarm_log.py) 负责事件与SQLite，[video_detection.py](../video_detection.py) 负责与视频生命周期连接。原报警规则没有新增Python依赖；后续媒体阶段调用本机FFmpeg。当前没有训练新权重，摄像头、像素掩码与模拟位置仍按后续计划推进。
